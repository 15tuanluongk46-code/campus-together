# Backend repair and admission hardening

Approved: fix the backend audit findings while preserving the current frontend, Solo and Co-op content.

## Requirements
1. Co-op launch selects two distinct contributing holders, one per station. Preserve that pair while both remain valid for 3 seconds. A redundant holder releasing, expiring, disconnecting or picking up must not reset progress. A contributing holder becoming invalid resets progress immediately; a replacement starts a fresh interval. Preserve Solo immediate reset and station-A latch semantics. Reset pair references on finish/replay/disposal.
2. All finish paths normalize gateOpen=false, gateUntil=0 and gateChargeMs=0 (including any charge/rearm bookkeeping as appropriate). Results never advertise an active gate countdown.
3. Use shared PROTOCOL_VERSION for domain join, health and client transport declarations rather than duplicated protocol literals. No protocol bump or sequence/dedup policy change.
4. Bound room admission before expensive room initialization. Defaults: maximum 32 initializing+live rooms per server; room-creating requests token bucket per canonical remote IP burst 6, refill 1 per 10 seconds. Apply to all public matchmaking paths capable of allocating rooms, not just the convenient client path. Trusted network peer address by default; never trust arbitrary X-Forwarded-For. Document supported proxy configuration if implemented. Bound and expire IP accounting (maximum 4096 entries, 10 minute idle expiry; when saturated reject new identities rather than silently bypass limits). Return clear retryable errors, preserve existing room join/reconnect. Reservations released exactly once on init failure/disposal/shutdown. No room IDs, IPs or player names in public health payloads.
5. Preserve GET /health liveness response ok/protocol compatibility. Add GET /ready readiness reporting only aggregate status: starting, ready, degraded or draining, room count/capacity and simulation freshness. No rooms is healthy. Allow at most 5 seconds startup grace for a room, then stale successful simulation heartbeat over 2 seconds makes readiness 503. A tick exception is caught, recorded and not falsely acknowledged as healthy; affected room must safely stop/dispose rather than continue corrupt state. Readiness is not a promise that an event-loop-blocked process can answer HTTP. During graceful shutdown readiness must fail before accepting new rooms.
6. Tests: redundant holders and contributor changes across release/expiry/disconnect/pickup with 3 and 4 players; gate finish charge/countdown; unchanged Solo three layouts and Co-op 2/3/4 full rounds; reconnect/items/replay/invalid requests; actual HTTP matchmaking throttle, cap concurrency, bypass paths, malformed requests, fake forwarded headers, bounded identities, init failure and disposal; readiness empty/fresh/stale/failed/draining. Use fake clocks for thresholds and real sockets for integration. No production teleport/debug bypass.
7. Document configuration, operational limits and exact verification. Build a clean immutable archive, verify it and smoke extracted Solo/Co-op before replacing localhost. No frontend redesign, no public deploy, no commits, no user/global config edits.

## Decisions
- Stable contributing pair avoids granting accumulated time to a replacement who has not held continuously.
- Defaults are conservative pilot settings, not measured capacity claims. Deployment limits can be explicitly configured and validated at startup.
- Existing authoritative item, sequence, reconnection and request dedup semantics remain binding.
